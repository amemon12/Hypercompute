# bench: plan, run and report Hypercompute benchmarks

`hcbench.py` wraps the paper driver that produced every number in `docs/pitch/NUMBERS.md`. It has three commands.

| Command | What it touches |
|---|---|
| `plan` | Writes one plan file. Checks every row with `run_big.py`'s own `parse_args`. No network. |
| `run` | Starts `scripts/capacity/paper/matrix.py` and nothing else. A real run needs `--yes`. `--dry-run` prints each row's command. |
| `report` | Reads the index files and run records and writes `bench/RESULTS.md`. No network. |

Run every command from the repo root with the repo venv:

```
uv run --no-sync python bench/hcbench.py <command> ...
```

Files:

- `hcbench.py`: the command line, `plan` and `run`.
- `hcbench_report.py`: the report arithmetic and the RESULTS.md layout.
- `pairs.json`: which groups of rows form a pair, their conditions, and the NUMBERS.md values to check.
- `RESULTS.md`: generated by `report`. Do not edit it by hand.
- `tests/`: unit tests on fixtures, and parity tests against the real records and `stats.py`.

## How a run works

`matrix.py` reads the plan. For each row it waits for the previous engine to drain, waits until every peer of the
row is eligible, snapshots `/api/network`, runs `run_big.py` in `HC_PAPER_REPO`, and appends one JSON line to the
index. `run_big.py` gets the owner token from `/api/owner/bootstrap`, which only answers on loopback, so a run must
start on the host machine itself. The token is never printed or recorded.

Two things to know before a real run:

- `matrix.py` talks to the gateway on `127.0.0.1:8001`. Start the host with `--port 8001`. The CLI default is 8000.
- A row that ends `infeasible` or `refused` is retried once after 60 s. The first attempt stays in the index as
  `<label>-refused`.

`matrix.py` waits only for peers to be eligible. It does not check the path type or the RTT. The R7 rows waited
until both Macs were direct under 30 ms (NUMBERS condition L7), so check the dashboard before a pooled row.

`run` holds `<index>.lock` while the driver runs, so two `hcbench run` calls cannot append to one index. A
`matrix.py` started directly, for example by `gx10/matrix.sh` or the live campaign, takes no lock, so do not point
it at an index an `hcbench run` is using. Ctrl+C reaches the driver and `run_big.py`, which stops its deployment.
`run` waits for them and returns the driver's exit code.

## Set up the pool

Host. On the machine that runs the gateway:

```
uv run --no-sync hypercompute host --transport iroh --port 8001 --no-browser
```

The host prints a live invite at startup. Keep its output out of logs you share. On the GX10 the same command is in
`scripts/capacity/paper/gx10/host.sh`, which also sets `HYPERCOMPUTE_LLAMA_BIN_DIR`.

Invites. Mint one per peer on the host. Each is good for one join within 15 minutes:

```
uv run --no-sync hypercompute invite --port 8001
```

It prints `uv run hypercompute join --ticket <TICKET> --code <CODE>`. Pass the ticket and code to the peer over a
private channel. Never paste them into a shared doc or a log.

Mac peers. Once per Mac, `scripts/capacity/paper/mac_bootstrap.sh` installs the code from a git bundle at
`~/hypercompute.bundle`, then the pinned engine. Then join in the background:

```
scripts/capacity/paper/mac_join.sh <TICKET> <CODE> mac-a <MAX_MEMORY> <RESERVE> --managed --max-disk <SIZE>
```

`--seed-peers` rows need peers joined with `--managed` and a `--max-disk` that holds their layers. The caps used:
10.5 GiB per Mac in L7, 11.5 GiB for mac-a and mac-b and 7.5 GiB for mac-c in G6, 7.5 GiB per Mac in B1
(NUMBERS condition keys). `gx10/rejoin_mac.sh` mints an invite on the GX10 and runs `mac_join.sh` over SSH. Its
output is redacted.

G14 as a GX10 peer. `scripts/capacity/paper/gx10/join_g14.sh` mints an invite over SSH and joins with CUDA0, a 9 GiB
cap, `--managed` and a 24 GiB disk cap. It holds the GX10's SSH address and the live-host path, so edit both for
another setup.

Node ids. Plans name peers by their 32 hex node id. Read them on the host's dashboard, from the SDK's
`Pool().nodes()`, or from `/api/nodes` on loopback.

## Reproduce each result family

Each family below gives the plan and run commands, then the pair to add to `pairs.json` if the labels are new.
Replace `<date>`, the node ids and the index names. Run `--dry-run` first, then the same command with `--yes`.

hcbench names rows `{tag}-{host}A-{k}` alone and `{tag}-{host}P{peers}-{k}` pooled. Tags and host names are
lowercase letters and digits only, so no label prefix catches another group. Most R7 labels already follow this.
The R6 rows used older names (`671b-gx4-1`, `g120-n1-gxA-1`), so a rerun gets new prefixes and a new pair entry.

### 1. Laptops: the G14 alone vs the G14 with MacBook Airs

Conditions L7 (home network, mac-a and mac-b) or B1 (building Wi-Fi, three Macs). Pairs `d70`, `g120`, `vl72`,
`n80` (L7) and `r2-3mac`, `r2-1mac`, `r1-235b` (B1). R7 used A P A P for headline models and one A P pair for the
rest. Example, Llama 3.3 70B as in R7.2:

```
uv run --no-sync python bench/hcbench.py plan --tag d70 --model llama-3.3-70b-instruct-q4_k_m --host g14 --peer <mac-a id> --peer <mac-b id> --order APAP --prompt-tokens 64 --output-tokens 32 --reps 2 --max-commit-growth-gib 8 --seed-peers --out results/capacity/paper-<date>-laptop/plan_d70.json
uv run --no-sync python bench/hcbench.py run results/capacity/paper-<date>-laptop/plan_d70.json --index results/capacity/paper-<date>-laptop/index_d70.jsonl --dry-run
```

The other R7 rows differ only in model and lengths: gpt-oss-120b and Qwen3-Next-80B at 128/64 with 3 reps, the
Qwen2.5-VL 72B at 64/32 with 2 reps and `--max-commit-growth-gib 24`. The commit guard values are guards, not
measured numbers (NUMBERS section 6). To pin the placement of later pooled rows, pass `--layout` with the layout of
the first pooled row. `plan` warns about the two stage kinds the gateway refused in R7: a peer stage on an `RPC`
device and a local `CPU` stage.

### 2. GX10 host: alone, and with four peers

Condition G6 for the pairs `671b` and `kimi`, GXA for the alone group `gx10-120b`. On the GX10, from
`~/hypercompute`, with `--preset gx10`, which sets exactly what `scripts/capacity/paper/gx10/matrix.sh` sets:

```
uv run --no-sync python bench/hcbench.py plan --tag 671b --model deepseek-v3.1-ud-tq1_0 --host gx --peer <g14 id> --peer <mac-a id> --peer <mac-b id> --peer <mac-c id> --order APAP --prompt-tokens 64 --output-tokens 32 --reps 2 --seed-peers --out results/capacity/paper-<date>/plan_671b.json
uv run --no-sync python bench/hcbench.py run results/capacity/paper-<date>/plan_671b.json --index results/capacity/paper-<date>/index_671b.jsonl --preset gx10 --dry-run
```

The pair is then `671b-gxA` vs `671b-gxP4`. The 1T is the same with `--tag kimi --model kimi-k2.6-iq1_s`. The GX10
alone on gpt-oss-120b is `--tag 120b --host gx --order AAA` with no `--peer`, 128/64 and 3 reps. NUMBERS 3a keeps
that number out of the pitch.

### 3. Concurrency: N chats at once

Each plan holds one N. `--concurrency N` must leave room for N x (prompt + answer) in `--ctx` (one unified KV pool);
`plan` rejects it otherwise with run_big's own message. Put N into the tag, as the campaign did.

Laptops, pooled vs alone at the same N (pairs `g120n4`, `g120n8`, condition L7):

```
uv run --no-sync python bench/hcbench.py plan --tag g120n4 --model gpt-oss-120b-mxfp4 --host g14 --peer <mac-a id> --peer <mac-b id> --order AP --concurrency 4 --max-commit-growth-gib 24 --seed-peers --out results/capacity/paper-<date>-laptop/plan_g120n4.json
```

GX10 alone, N vs N = 1 (pairs `g120gx-n4`, `g120gx-n8`, `kimigx-*`, `ds671gx-*`, condition GXA). R6.y interleaved the
120B rows n1 n4 n8 n8 n4 n1. Write five plans and run them in this order into one index, with `--append` after the
first:

| Plan | Flags besides `--model gpt-oss-120b-mxfp4 --host gx` | Rows |
|---|---|---|
| 1 | `--tag g120n1 --order A` | g120n1-gxA-1 |
| 2 | `--tag g120n4 --order A --concurrency 4` | g120n4-gxA-1 |
| 3 | `--tag g120n8 --order AA --concurrency 8` | g120n8-gxA-1, g120n8-gxA-2 |
| 4 | `--tag g120n4 --order A --concurrency 4 --start 2` | g120n4-gxA-2 |
| 5 | `--tag g120n1 --order A --start 2` | g120n1-gxA-2 |

The 1T and 671B rows were one row per N at 64/32 with 2 reps (`--prompt-tokens 64 --output-tokens 32 --reps 2`).

A new pair for these rows is `"kind": "n_vs_n1"`, `"mode": "batches"`, `"a_prefix": "g120n1-gxA"`,
`"b_prefix": "g120n8-gxA"`. R8 also measured pooled GX10 concurrency for Maverick at N = 4 and 8 and Kimi at N = 8; see NUMBERS section 3e.

## Report

```
uv run --no-sync python bench/hcbench.py report
uv run --no-sync python bench/hcbench.py report --check
```

`report` reads `results/capacity/paper-2026-10-2*/index_*.jsonl` in sorted order and the run records under
`--results-root`, else `$HC_PAPER_REPO/results/capacity`, else this repo. A last index line that is not valid JSON
(a live append) is skipped with a warning. A bad line anywhere else stops the report. `--check` exits 1 when
RESULTS.md is out of date and writes nothing.

The retired `ds671-g3` comparison combined runs from separate sessions and is excluded from active report pairs.
Use `ds671-g3-interleaved` for the 671B comparison: its alternating runs measured decode parity. The original
individual run records remain in the report for auditing; they are not evidence for a pooled decode gain.

The arithmetic is the paper scripts' own. Per-row values are `summarize.py`'s `row()`, plus seeding seconds and the
median first token. Pairs are `stats.py`: label prefix, status ok, reps from N = 1 runs or ok batches at N > 1,
ratio of means B/A, percentile bootstrap with `random.Random(7)` and 10,000 resamples. First token and full answer
follow `ttft_stats.py` and `conc_ttft.py`, the scratchpad scripts NUMBERS.md names. A group whose mean is 0 prints
`n/a (mean 0)`, where `stats.py --batches` divides by zero. A pair with `only_labels` gets a line under its table
with the matching `stats.py --only-labels` list and the ok runs it leaves out; section 3 names that pair for them.
SSD MiB values print at the decimals NUMBERS.md quotes, else 3 decimals under 1 MiB and 1 decimal above.

To add a pair, append an object to `pairs` in `pairs.json` with `id`, `family`, `kind`, `condition`, `model`,
`prompt_answer`, `n`, `a_prefix`, `b_prefix`, `indexes` (relative to `results/capacity/`), `only_labels` (list or
null), `mode` (`reps` or `batches`), `metrics` and `numbers_ref`. Add `expect` only with values copied from
NUMBERS.md. Section 4 of RESULTS.md lists every value that differs.

## Tests

```
uv run --no-sync python -m pytest bench/tests -q
```

The tests open no socket. `run` tests use a stub `matrix.py` in a temporary repo. The parity tests read the real
records, compare every row with `summarize.row`, every value of PACKAGING-SPEC 4.5, and `stats.py` run as a
subprocess. They skip when `results/capacity/paper-2026-10-24-laptop` is missing.

## Implementation notes

- The benchmark contract is section 4 of `docs/PACKAGING-SPEC.md`.
- There is no `--matrix` flag. `run` only starts `<repo>/scripts/capacity/paper/matrix.py`, where `<repo>` is
  `--repo` (or the preset's repo) or this checkout. The tests point `--repo` at a stub.
- A real `run` needs `--yes`. `--dry-run` does not.
- Additions to the spec: `plan --start`; the `answer` metric; first token at N > 1 uses ok batches only
  (`conc_ttft.py` used every batch, and every R7.5 and R6.y batch was ok); `pairs.json` has `families`, `singles`,
  `row_checks`, `expect` and the kind `pooled_vs_pooled`; RESULTS.md section 3 also lists ok rows that no pair uses.
- Spec 4.6 gives 8 x (128 + 64) > 4096 as a KV overflow. That is 1536 and fits. The test uses 8 x (512 + 64) = 4608.
- The parity tests pin the R7 laptop pairs to the rows NUMBERS used, because the campaign may append a second d70
  pair. RESULTS.md uses every row, so section 4 will flag NUMBERS values that new rows change.
- `hcbench.py` and the test conftest set `sys.dont_write_bytecode`, so no `.pyc` lands under `scripts/` or
  `backend/` of the campaign checkout.
