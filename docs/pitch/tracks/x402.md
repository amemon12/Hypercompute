# Best Use of x402 by Coinbase (Cal Hacks 13.0): $500 USDC plus a recruiter call per team member, per track

Fit 6.5/10, prize about $2000, effort about 5 h (estimate).

## Integration

Candid fit check: an x402 paywall in front of an LLM is one of the most common x402 demos, so payment alone will look bolted on. What makes it real work here is the split. Each settled payment is divided by what each friend's machine actually served in that run, using the deployment plan the planner already produces. Refunds also come for free: the x402 FastAPI middleware does not settle when the handler returns a status of 400 or higher, so a buyer is never charged when the pool is not ready (503) or a peer drops mid-chat (ChatInterrupted).

Smallest real build. It is opt-in and only switches on when HYPERCOMPUTE_X402_PAY_TO is set.

1) Dependency. Add an optional extra to pyproject.toml: pay = ["x402[fastapi,httpx,evm]==2.25.0"]. That is the PyPI release from 2026-09-29. Friends' peers never install web3.

2) New module backend/hypercompute/services/x402_pay.py (about 150 lines):
- A frozen X402Config read from env: PAY_TO (checked against ^0x[0-9a-fA-F]{40}$), PRICE (default "$0.01"), NETWORK (default eip155:84532, Base Sepolia), FACILITATOR_URL (default https://x402.org/facilitator, which I checked live: /supported lists exact, upto and batch-settlement on eip155:84532 with no API key), MAX_TOKENS (default 256), PAYEES ("mac-a=0x..,g14=0x..", mapping node display_name to a wallet; host-only, so the peer schemas stay unchanged, which matters because Model has extra="forbid") and HOST_FEE (default 0.10).
- build_middleware(): x402ResourceServer(HTTPFacilitatorClient(url=...)) with .register("eip155:*", ExactEvmServerScheme()). The routes map is {"POST /x402/v1/chat/completions": {"accepts": {scheme "exact", payTo, price, network}, "description": "<model> served by N friends' machines"}}, then payment_middleware(routes, server).
- split(plan, amount_atomic, host_fee): a pure function. Each node's weight is the sum of weight_bytes over its DeviceAssignment rows. The host node also gets plan.cpu_resident_bytes plus plan.moe.cpu_expert_bytes (the file-backed experts on the GB10). Amounts are integer USDC atomic units. The remainder and any node without a payee address go to the host.
- An outer wrapper middleware around the x402 one. When the reply has a PAYMENT-RESPONSE header, it decodes it with x402.http.utils.decode_payment_response_header (success, transaction, payer, network) and reads the run id that the handler put in an X-Hypercompute-Run header. It writes a row to a new SQLite table and calls coord.events.publish("x402_settled", ...) with the tx hash and the shares.

3) backend/hypercompute/storage.py: CREATE TABLE IF NOT EXISTS x402_payments (id, run_id, tx, payer, network, amount_atomic, shares_doc, created_at).

4) backend/hypercompute/app.py (about 40 lines):
- When the config is enabled, register the wrapper middleware before SecurityHeadersMiddleware so 402 replies still carry the security headers.
- Add a new POST /x402/v1/chat/completions. It skips OwnerWrite because payment is the auth (the /v1 route stays owner and loopback only). It reuses the validation from the existing chat handler, forces stream=false (the x402 middleware buffers the whole body before it settles anyway), clamps max_tokens to MAX_TOKENS, rejects resume_from, calls coord.inference.chat_complete and sets X-Hypercompute-Run from the recorded run.
- Add an owner-only GET /api/x402/ledger that returns per-node USDC totals and recent payments.

5) Frontend:
- api/client.ts gets getLedger().
- PeerCards.tsx shows "earned 0.0123 USDC" for each friend.
- ActivityFeed.tsx already renders any event type. Linkify x402_settled events to https://sepolia.basescan.org/tx/<hash>.

6) scripts/x402_buyer.py, the buyer agent: x402Client registered for eip155:* with ExactEvmScheme(EthAccountSigner(Account.from_key(env X402_BUYER_KEY))) and spend_controls {"max_amount_per_payment": "$0.05"}, run through x402HttpxClient. It prints the 402 price, the answer and the settlement tx.

7) tests/test_x402_pay.py:
- split sums exactly to the amount, the remainder goes to the host, and nodes without a payee fold into the host;
- no x402 route exists when the env var is unset;
- an unpaid POST gets a 402 with a PAYMENT-REQUIRED header, using a stub facilitator;
- an error response is not settled.

Data flow: buyer POST, then 402 with PAYMENT-REQUIRED, then the buyer signs an EIP-3009 USDC authorization and retries with PAYMENT-SIGNATURE. The facilitator verifies, the existing inference service runs on the llama.cpp RPC pool, and a 200 settles on Base Sepolia. The wrapper then splits by plan bytes into the ledger, and the event shows up on the dashboard.

Stretch options:
- (a) Settle-up button, about 1.5 h: POST /api/x402/payouts sends each payee's accrued test USDC from the pay_to wallet with web3 ERC-20 transfers, so the split happens on chain.
- (b) The "upto" scheme for real per-token metering: authorize max_tokens x a per-token price, then settle completion_tokens x that price with set_settlement_overrides. This is riskier because it needs a Permit2 approval.

## Demo moment

A second laptop runs `python scripts/x402_buyer.py "Explain MoE routing in two sentences"` as an AI agent with its own Base Sepolia wallet. The terminal shows HTTP 402: 0.01 USDC on Base Sepolia. The agent signs, retries, and the answer from the pooled model comes back. At the same moment the dashboard activity feed shows x402_settled with a BaseScan link (open it: a real on-chain USDC transfer). Each friend's peer card ticks up by its share of the layers it served: the GX10 gets most (layers 14-60 plus the CPU experts), and the G14, mac-a, mac-b and mac-azim each get their 3 to 5 layers. Close with one line: "if a friend's machine drops or the pool isn't ready, the request fails and nothing is settled, so the buyer only pays for compute that was actually delivered." Show this with a request sent while the deployment is stopped (503 and no charge). Do not kill a peer live: a 671B reload takes 4 to 8 minutes. Use gpt-oss-120b or max_tokens of about 48 for the paid call so it finishes in seconds (56 tok/s on the GX10 in R6, versus about 1.5 tok/s for the pooled 671B).

## Accounts and keys (the user creates these)

Create and manage these credentials manually. Keys go only in env vars, never in the repo.

1) Seller receiving address (public address only, no key on the gateway): a Base Sepolia wallet from Coinbase Wallet, the CDP portal or MetaMask, set as HYPERCOMPUTE_X402_PAY_TO.

2) Buyer test wallet: generate a throwaway key, set it as X402_BUYER_KEY on the buyer machine and fund the wallet with Base Sepolia test USDC from Circle's faucet (faucet.circle.com). It needs no ETH, because with EIP-3009 the facilitator pays the gas.

3) Optional friend payout addresses in HYPERCOMPUTE_X402_PAYEES (their own wallets, public addresses only).

4) No CDP API key is needed for the public https://x402.org/facilitator on Base Sepolia. A CDP account with CDP_API_KEY_ID and CDP_API_KEY_SECRET (plus cdp-sdk) is only needed if the track requires the CDP facilitator, mainnet or Bazaar listing. Check the starter pack PDF for this.

5) Settle-up stretch only: the pay_to wallet's private key in HYPERCOMPUTE_X402_PAYOUT_KEY, plus Base Sepolia ETH for gas from a faucet. Testnet only.

## Risks

1) The criteria are unverified. The starter pack (Google Drive PDF) does not render without sign-in, and I did not pull the raw file download without your approval. If it requires CDP products (CDP facilitator, Server Wallet, Bazaar, mainnet), switch the facilitator URL to CDP and add the keys.

2) Novelty: pay-per-call LLM gateways are a stock x402 demo. The edge depends on visibly crediting each friend by the layers they served, and on no settlement when the pool fails. Without the split shown on the dashboard it reads as bolted on.

3) The split is an off-chain ledger unless the settle-up stretch ships. Judges may call that bookkeeping, and on-chain payouts mean handling the owner's private key (testnet only).

4) Reachability: in Iroh mode the gateway binds to 127.0.0.1 only (cli.py refuses --bind with iroh). An external buyer needs the host in LAN mode with --bind, or a tunnel. Otherwise run the buyer on the host itself. A pay-only route on venue Wi-Fi also needs a concurrency guard.

5) Streaming: the x402 FastAPI middleware buffers the full body before it settles (fastapi.py lines 380-383). Paid calls are therefore effectively non-streaming, and pooled 671B at about 1.5 tok/s is too slow on stage. Use 120B or a short max_tokens.

6) Contention: the paid route shares the inference slots. Overnight benchmarks and tuner runs hold all slots, so a paid call during them waits up to 30 s or fails. It is uncharged, but the demo breaks.

7) Dependencies: x402[evm] pulls web3, eth-account and ckzg. The install on the aarch64 GX10 (DGX OS) could fail or take time. Install it in a separate venv off the benchmark critical path, and pin 2.25.0.

8) External dependency on the public x402.org facilitator and Base Sepolia. Settlement can return settlement_pending on an RPC timeout, so show the tx link only when success is true.

9) Prize value assumes a 4-person team ($500 each). It is $500 for a solo entry. The second Coinbase track is separate.

10) The repo was read-only for this pass. Nothing is implemented or verified yet.
