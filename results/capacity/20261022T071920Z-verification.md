# Verification of the 2026-10-22 calibration, ranking and pair reports

Verifier: adversarial re-check from the evidence files only. No hardware was run: no bench, probe, explain_host or
engine call. What I did run: Python over the JSON evidence, `pytest` on the capacity tests, `ruff`, `git log`,
`git diff`, and a read-only `netstat`. No llama-server or llama-completion process was running before or after.

All paths are under `C:\Users\operator\.hypercompute\worktrees\iroh-transport\results\capacity\` unless absolute.

## Verdict

- Calibration: every stored and reported number recomputes from its evidence. A few labels and side claims are
  wrong or have no evidence (list below). No coefficient needs to change.
- Ranking: every prediction recomputes. Nothing was measured, so there is no rank correlation or error to check.
  The rank-correlation and percent-error code is correct. Two defects in the files and the runner are listed below.
- Pair: every prediction recomputes. The power wattage is internally inconsistent, one load term is not named, and
  the "39x" ratio rests on an unmeasured extrapolation.
- No failed run was dropped. Warmups are excluded everywhere. Decode is `predicted_ms / (predicted_n - 1)` from
  engine timings in every run used.

## Corrections needed

1. Calibration, battery range. The report says the battery was "between 10% and 19%". The evidence records 13% at
   06:26:37Z (dry runs) and 20% for every rep of the GPU run (`20261022T062921Z-...-stock-gpu\bench.json`). No file
   records 10%. Say 13% to 20%.
2. Calibration, power evidence. "PowerOnline was True before every one" is not in any file. What the files show:
   bench.json records `psutil.sensors_battery` source `ac` for the host and every rep, and storage.json records
   `Win32_Battery.BatteryStatus` 2 (AC). `link.json` records no power state, and both link records are stored with
   `power_state: null`. Say which API backs which run, and that the link probe has no power evidence.
3. Calibration, the stored-records header. "build b11770, ctx 2048" does not apply to the storage row. Its build is
   `storage_probe-4r-8MiB` and its ctx is null.
4. Calibration, GPU memory. 4612 MiB is the device-wide `used_mib` from nvidia-smi. The engine's own usage was not
   recorded (`process_used_mib: null`), so the number includes every other GPU user.
5. Calibration, test count. "The full capacity suite passes (645)" does not reproduce. The suite now collects 643
   tests without `tests/test_capacity_rank.py`, and 678 with it (678 passed, 1 deselected by the `hardware`
   marker). The ranking report's 678 is correct.
6. Calibration, "8 for the 7B (6 before that)". There is no saved command output. The store is consistent with 2
   records for the 0.5B and 8 for the 7B. "(6 before that)" is unexplained.
7. Calibration, explain_host output. There is no saved file for the J = 5911 ms breakdown. The arithmetic is right
   (2728.69 + 126.735 + 256 x 11.9348 = 5910.74 ms), and ranking.json `measured_coefficients` confirms that CPU,
   CUDA0 and storage resolve to the measured records. Save the output next time.
8. Ranking, inventory time. "Inventory from 00:35Z" is only partly right. The snapshot file was taken at 06:30:22Z.
   The local node's `collected_at` is 00:35:30Z (the device list), but its VRAM free is from 06:30:15Z, and host RAM
   in ranking.json is a live reading at the run (06:55:51Z).
9. Ranking, `order_matches: true` with `n: 0`. In all three ranking.json files, `ranklib.ranking` returns
   `[] == []`, which is True. It should be null when fewer than 2 layouts are measured. This is a code defect in
   `scripts/capacity/ranklib.py` (`ranking`, line 414).
10. Ranking, e16 feasibility in the file. The e16 row records `optimizer_feasible: true` with no reasons, but its
    own `layout_cpu_demand` says `fits: false` (3.725 GiB peak against 2.807 GiB admissible). Its 78.55 ms
    prediction is for an all-resident layout the planner would not admit. The prose report says this, but
    ranking.json carries no warning. Also, `rank_layouts._gate` skips only GPU overflow, so a listed CPU-overflowing
    layout like e16 would be run. The proposed AC command leaves e16 out, which is correct.
11. Ranking, battery reps. `ranklib.ranking` ranks any row with at least 3 measured reps. It does not exclude a row
    whose reps include `battery` in `measured.power`. One AC check before each layout cannot catch a mid-run power
    loss, which happened at about 06:41Z tonight. Exclude or flag such rows before the AC run.
12. Ranking, file length. `rank_layouts.py` is 529 lines (`wc -l`), not 528. This is trivial.
13. Pair, wattage. The report gives a 35 to 42 W discharge, but RemainingCapacity 14234 to 9978 mWh between
    07:00:39Z and 07:05:01Z is 4256 mWh in 4.37 min, about 58 W. At 58 W, 9978 mWh lasts about 10 min, not about 15.
    No PowerShell output is saved for any of these readings. The psutil percent in the pair dry runs (17% at
    07:04:50Z) and ranking dry runs (30% at 06:55:52Z, 28% at 06:57:29Z) confirm battery but give no wattage.
14. Pair, load terms. "Uploaded bytes at 1.585e6 bytes/s plus the 2000 ms setup priors" leaves out two terms: the
    500 ms per-remote-stage prior (`SETUP_MS_PER_REMOTE_STAGE`) and the local SSD read. Layout b is
    13730.8 (upload) + 2000 + 500 + 61.7 (370092032 bytes at 5.998e9 bytes/s) = 16292.5 ms. Layout c is
    38985.2 + 2500 + 55.0 = 41540.2 ms. Name the 500 ms prior.
15. Pair, the "39x slower" ratio. The 1.07 ms/token for the 0.5B on CUDA0 is the 7B's per-GiB coefficient
    (2.932 ms/GiB) times 0.3649 GiB. No 0.5B GPU run exists (`20261022T024342Z-stock-q05b` is CPU, `--device
    none`). Tonight's CPU data shows per-GiB cost is not size-invariant: the 0.5B costs 1.33x the 7B per GiB. So
    1.07 ms is probably optimistic and the 39x ratio is unreliable. The roughly 40.5 ms/token difference, almost all
    relay hop, is the robust part. Drop "39x" or label it as resting on that extrapolation.
16. Pair, "eligible again at 07:04:46Z". No saved file shows it. `nodes-0700Z.json` holds only the 07:00:57Z state,
    written at 07:05:24Z.
17. Link goodput sample count. The stored `link.goodput_bytes_per_s` has 1 sample with no warmup and no spread,
    below the 3-rep rule the compute coefficients follow. It was disclosed. The 05:42Z probe (1581014 bytes/s,
    also n = 1) agrees within 0.3%. Keep it labelled n = 1 wherever it is used.

  short of 512.

  passed. Full capacity suite: 678 passed, 1 deselected.
- `ruff check --no-cache` on the 7 changed or new files: clean.
- Only `benchlib.py` and `tests/test_capacity_bench.py` are modified among tracked files. The new scripts and tests
  are untracked. Nothing is committed.
